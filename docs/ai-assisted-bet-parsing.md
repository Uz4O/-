# AI 辅助投注解析可信方案

## 1. 背景

本项目服务的主要用户是“计算者”。实际业务链路是：

```text
投注者发送投注信息
→ 计算者收集截图或聊天文本
→ 计算者计算投注金额和中奖金额
→ 计算者向庄家汇报
```

投注者不会按照系统要求统一格式发送内容，且计算者通常一次处理很多条投注信息。因此，方案不能要求投注者改变输入方式，也不能要求计算者逐条复核，否则会违背工具“减少计算工作量”的核心价值。

当前系统已经有一套确定性计算逻辑，支持平码、连码、数字复式、生肖复式等模式。问题在于真实投注文本格式很多，单靠规则解析器适配所有写法不现实；单靠 AI 又无法保证百分之百准确。

本方案目标是在不增加计算者大量工作量的前提下，提高自动解析覆盖率，并保证最终计入金额具有可追溯、可验证、可审计的可信度。

## 2. 核心原则

### 2.1 AI 不能直接决定最终金额

AI 可以参与文本整理、格式归一、候选分类和字段抽取，但不能直接给最终金额，也不能凭自己的理解把新格式自动计入可信总额。

最终金额必须由本地确定性规则引擎计算。

### 2.2 已认证规则才可以自动计入

一条投注要自动计入总金额，必须同时满足：

- 匹配到一个已认证规则 ID。
- 提取出完整字段，例如玩法、号码、生肖、金额、金额单位。
- 能生成确定性计算公式。
- 规则引擎计算成功。
- 不存在 OCR 低置信度、字段冲突、金额歧义等异常。

不满足这些条件的投注不能自动计入可信总额。

### 2.3 未知格式不自动算

如果遇到新格式，系统可以让 AI 给出候选解释，但不能自动采纳。

系统应提示计算者选择模式：

```text
平码
连码
数字复式
生肖复式
```

用户选择模式后，系统按该模式尝试解析并展示公式预览。确认后，该条才可以计入，并可以沉淀为新的已认证规则样本。

### 2.4 计算证据必须可见

系统不能只显示总金额。每条自动计入的投注都应能展示计算证据，例如：

```text
平特一肖牛买1200 = 牛 1肖 × 1200 = 1200
鸡马虎龙猴蛇 一个号20 = C(6,3) × 20 = 400
21.47.12.36 各50 = 4码 × 50 = 200
```

计算者不需要逐条修改，但必须能快速抽查公式，发现明显不合理的解析。

## 3. 推荐总体流程

```text
OCR 或粘贴原文
→ 文本清洗
→ 子投注切分
→ 已认证规则库匹配
→ 规则引擎确定性计算
→ AI 仅处理未匹配项并给出候选
→ 新格式让用户选择模式
→ 公式预览
→ 用户确认后计入
→ 保存确认样本和规则版本
```

## 4. 模块设计

### 4.1 OCR / 原文输入层

输入来源包括：

- 聊天截图 OCR。
- 表格截图 OCR。
- 用户手动粘贴文本。

OCR 输出必须保留原文，不能只保留清洗后的文本。每条投注最终都应能追溯到原始文本片段。

OCR 应尽量输出字段置信度，尤其是：

- 数字号码。
- 金额。
- 生肖字。
- 玩法关键词。

低置信度字段应进入异常状态，不应直接自动计入。

### 4.2 文本清洗层

文本清洗只处理确定无歧义的归一化，例如：

- `侯`、`候` 统一为 `猴`。
- 中文金额别名：`佰`、`百`。
- 全角标点和半角标点统一。
- 多余空格清理。

文本清洗不能改变投注语义。例如不能把 `一个号20` 强行解释成每号或每组，必须交给模式和规则决定。

### 4.3 子投注切分层

一条消息可能包含多种玩法，例如：

```text
羊鸡猪牛复四三各五十平特羊又鸡各一佰
```

系统需要先切分成子投注：

```text
羊鸡猪牛复四三各五十
平特羊又鸡各一佰
```

再分别归类和计算。

切分结果也必须保留来源范围，方便回溯。

### 4.4 已认证规则库

规则库保存经过确认的格式模式，不保存 AI 的自由判断。

每条规则至少包含：

```json
{
  "ruleId": "zodiac_group_sanzhong3_v1",
  "version": 1,
  "status": "certified",
  "mode": "zodiacFushi",
  "play": "三中三",
  "amountUnit": "per_combo",
  "matchPattern": "多组生肖 + 一个号金额",
  "calculation": "每组 C(生肖数,3) × 金额",
  "examples": [
    "鸡马虎龙候蛇，鸡马龙虎猴蛇，虎鸡兔狗候龙，一个号20"
  ]
}
```

规则必须绑定：

- 模式。
- 玩法。
- 金额单位。
- 计算公式。
- 版本号。
- 示例样本。

不能只绑定文字模板，因为相同文字在不同模式下可能有不同含义。

### 4.5 AI 标准化层

AI 的职责是生成候选结构，不是最终裁判。

AI 可以输出：

```json
{
  "sourceText": "平特一肖牛买1200",
  "candidates": [
    {
      "mode": "pingma",
      "play": "平特一肖",
      "zodiacs": ["牛"],
      "amount": 1200,
      "amountUnit": "per_zodiac",
      "confidence": 0.93
    }
  ]
}
```

AI 输出后必须经过规则引擎校验：

- 是否命中已认证规则。
- 字段是否完整。
- 金额单位是否明确。
- 是否能生成公式。
- 是否与原文关键字段一致。

未通过校验的候选不能计入可信总额。

### 4.6 规则计算器

规则计算器是唯一负责最终金额和中奖金额的模块。

它只接受结构化输入，例如：

```json
{
  "mode": "zodiacFushi",
  "play": "三中三",
  "zodiacGroups": [
    ["鸡", "马", "虎", "龙", "猴", "蛇"]
  ],
  "amount": 20,
  "amountUnit": "per_combo",
  "ruleId": "zodiac_group_sanzhong3_v1"
}
```

输出必须包含：

```json
{
  "betAmount": 400,
  "formula": "C(6,3) × 20 = 400",
  "ruleId": "zodiac_group_sanzhong3_v1",
  "ruleVersion": 1
}
```

## 5. 状态分类

每条投注应有明确状态。

### 5.1 自动可信

条件：

- 已认证规则匹配成功。
- 字段完整。
- OCR 关键字段无低置信度。
- 公式生成成功。
- 无规则冲突。

处理方式：

- 自动计入总金额。
- 显示规则 ID 和计算公式。

### 5.2 待选择模式

条件：

- AI 或规则识别出可能是投注。
- 没有匹配到已认证规则。
- 或存在多种合理解释。

处理方式：

- 不计入可信总额。
- 展示原文。
- 提供四个模式选项：平码、连码、数字复式、生肖复式。
- 选择后尝试解析并显示公式预览。

### 5.3 待确认

条件：

- 用户已选择模式。
- 系统可以生成候选公式。
- 但该格式尚未认证，或存在低置信度字段。

处理方式：

- 显示公式预览。
- 用户确认后计入。
- 可保存为新规则样本。

### 5.4 无法解析

条件：

- 无法识别玩法。
- 金额缺失。
- 号码或生肖不完整。
- 所选模式下无法生成公式。

处理方式：

- 不计入可信总额。
- 显示失败原因。
- 允许用户手动改文本或选择模式重试。

## 6. 新格式处理流程

当系统遇到新格式时，不应直接让 AI 决定。

推荐流程：

```text
发现未知格式
→ 展示原文
→ AI 给出候选解释
→ 用户选择模式：平码 / 连码 / 数字复式 / 生肖复式
→ 系统按该模式解析
→ 显示计算公式和金额
→ 用户确认
→ 计入总额
→ 保存样本
→ 后续相似格式可自动匹配
```

示例：

```text
原文：
鸡马虎龙候蛇，鸡马龙虎猴蛇，虎鸡兔狗候龙，鼠虎龙马猴狗，狗鸡兔龙马猪，马猪蛇候兔虎，
一个号20
```

用户选择：

```text
生肖复式
```

系统解析：

```text
6组生肖，每组6个生肖
玩法：三中三
金额单位：每组组合20
计算：6 × C(6,3) × 20 = 2400
```

确认后保存规则样本：

```text
多组生肖 + 一个号金额 → 生肖复式三中三 → 每组 C(n,3) × 金额
```

## 7. 批次级工作台设计

为了避免计算者逐条复核，页面应以批次视角展示：

```text
本次共识别 86 条
自动可信 80 条
待选择模式 3 条
待确认 2 条
无法解析 1 条
可信总金额 45200
暂未计入金额 1800
```

默认只展开异常项。

自动可信项只显示汇总，允许用户抽查。

异常项集中处理，用户不需要查看全部投注。

## 8. 公式预览设计

用户选择模式后，系统必须展示公式预览。

示例：

```text
模式：生肖复式
玩法：三中三
内容：鸡马虎龙猴蛇
金额：20 / 组
公式：C(6,3) × 20 = 400
```

如果一条消息包含多组：

```text
共6组
每组 C(6,3) × 20 = 400
合计：6 × 400 = 2400
```

用户看到公式后再确认，能显著降低误点模式造成的风险。

## 9. 主要风险与防线

### 9.1 OCR 识别错误

风险：

- `38` 识别成 `88`。
- `猴` 识别成 `候` 或 `侯`。
- `100` 识别成 `10O`。

防线：

- 关键字段低置信度标红。
- 金额和号码低置信度不自动计入。
- 保留原图局部或原文片段用于核对。

### 9.2 AI 自信但错误

风险：

AI 可能把新格式错误分类，并且看起来很合理。

防线：

- AI 候选必须匹配已认证规则才能自动计入。
- 未认证格式只能进入待选择或待确认。
- AI 不直接输出最终金额。

### 9.3 同一句存在多种业务解释

风险：

`一个号20` 在不同上下文中可能表示每号20，也可能表示每组组合20。

防线：

- 规则必须绑定模式和金额单位。
- 新格式第一次必须让用户选择模式。
- 公式预览必须展示金额单位。

### 9.4 用户选错模式

风险：

用户在四个模式中点错。

防线：

- 选择后展示公式预览。
- 显示解析后的号码、生肖、组合数。
- 明显不合理时提示，例如组合数为0、金额异常过大。

### 9.5 相似格式误套规则

风险：

已认证规则可能误匹配相似但含义不同的格式。

防线：

- 规则匹配条件要严格。
- 规则要有版本和样本覆盖。
- 金额单位、玩法关键词、分隔结构都要参与匹配。

### 9.6 规则变化影响历史结果

风险：

今天修改规则后，历史报表重新计算会变化。

防线：

- 每次计算保存结构化投注单、规则 ID、规则版本、公式和结果。
- 历史报表默认使用当时规则版本，不随新规则自动变化。

## 11. 实施阶段建议

### 第一阶段：异常队列和模式选择

目标：

- 新格式不自动计入。
- 提供平码、连码、数字复式、生肖复式四个模式选项。
- 选择后显示公式预览。
- 用户确认后计入。

这是最重要的一步，能先解决“未知格式被系统自信算错”的问题。

### 第二阶段：规则 ID 和公式留痕

目标：

- 每条自动计入的投注都保存规则 ID、规则版本和公式。
- 报表可以追溯每条金额来源。
- 历史结果不受未来规则修改影响。

### 第三阶段：AI 标准化候选

目标：

- AI 只处理未匹配项。
- AI 输出结构化候选 JSON。
- 候选必须经过规则校验。
- AI 不直接计入总额。

### 第四阶段：认证规则库沉淀

目标：

- 用户确认的新格式可保存为样本。
- 后续类似格式自动匹配。
- 规则匹配条件逐步完善。

### 第五阶段：OCR 关键字段置信度

目标：

- OCR 对金额、号码、生肖输出置信度。
- 低置信度字段进入异常队列。
- 必要时显示原图局部辅助核对。

## 12. 成功标准

系统不应承诺“自由文本全自动百分之百正确”。更准确的目标是：

- 已认证规则内的计算必须百分之百确定。
- 未认证格式不能自动计入可信金额。
- AI 错误不能直接污染最终总额。
- 计算者只需要处理异常项，而不是逐条复核全部投注。
- 每条计入金额都有公式和规则版本可追溯。

## 13. 结论

要同时满足“方便”和“可信”，不能依赖单一 AI，也不能无限堆规则。

推荐方案是：

```text
AI 做助手
规则库做裁判
计算器做最终金额
异常队列保护可信总额
用户只处理新格式和冲突项
```

这套方案的关键不是让 AI 永远判断正确，而是确保 AI 判断错误时不会自动进入最终金额。
